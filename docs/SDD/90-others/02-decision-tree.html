🌟 5 个实战场景

🌱 场景 1:从零开始的新项目

🅰️ 状态:项目方向完全模糊

典型表现:"我想做一个 AI 助手,但不知道具体要什么"

推荐组合:Superpowers brainstorming + awesome-claude-skills 的 deep-research

实操步骤

Step 1 · 安装(5 分钟)

# 在 Claude Code 中:
/plugin install superpowers@claude-plugins-official

# 装 deep-research skill:
mkdir -p ~/.config/claude-code/skills/
cp -r deep-research ~/.config/claude-code/skills/
claude

Step 2 · brainstorming 启动(1-2 小时)

> 我想做一个 AI 文档助手

# brainstorming 自动激活,问 5-10 个问题:
Q1: 给谁用?企业/个人/开发者?
Q2: 最痛场景?
Q3: 如果只有 1 个功能?
Q4: 不做什么?
Q5: 3 个月后成功了,长什么样?
...

Step 3 · deep-research 验证(1-2 天)

> 用 deep-research 调研 AI 文档助手竞品

Step 4 · 产出 design doc

输出 docs/superpowers/specs/2026-10-14-ai-doc-assistant-design.md

Step 5 · 进入 spec-kit

> /speckit-constitution  # 制定宪法
> /speckit-specify 文档上传功能
> /speckit-specify 智能摘要
...

🆕 场景 2:已有项目加新功能(本项目常遇到)

🅲️ 状态:方向清楚,具体功能模糊

典型表现:"我们 Deep Research Agent 要加答案溯源功能,大概怎么设计?"

推荐组合:OpenSpec explore + idea-autopsy(agentic-awesome-skills)

实操步骤

Step 1 · 安装(2 分钟)

npm install -g @fission-ai/openspec@latest
cd /path/to/project
openspec init

# 装 idea-autopsy:
npx agentic-awesome-skills --skills idea-autopsy

Step 2 · OpenSpec explore(30-60 分钟)

> /opsx:explore 我们想加答案溯源功能,有什么方案?
   - 阅读现有检索/推理/渲染代码
   - 给出 2-3 个方案对比
   - 列出 tradeoffs
   - 等你确认后进入 propose

Step 3 · idea-autopsy 压力测试(15 分钟)

> 用 idea-autopsy 检查答案溯源想法:
"如果只能 1 句话杀死这个想法,会是什么?"

Step 4 · 写 RFC(1-2 天)

基于 explore 的输出,写 RFC 文档(用上一轮我们讨论的 RFC 模板)

Step 5 · OpenSpec propose(30 分钟)

> /opsx:propose 答案溯源
   - 创建 openspec/changes/answer-citation/
   - 自动产出 proposal.md, specs/, design.md, tasks.md

Step 6 · 进入 spec-kit(逐个 feature)

> /speckit-specify 片段 ID 生成器  # FEATURE-007
> /speckit-specify 引用映射插入     # FEATURE-008
> /speckit-specify 引用渲染组件     # FEATURE-009
...

为什么这个组合最合适:

  • OpenSpec explore 读你的代码,给具体方案
  • idea-autopsy 找盲点,防止"漏掉"边界情况
  • OpenSpec propose 产出完整 change 包(proposal/specs/design/tasks)
  • spec-kit 接手逐个 feature的精细化

🤝 场景 3:跨团队 RFC 前的发现

🅱️ + 🅲️ 状态:跨团队影响,需要"压力测试"想法

典型表现:"这个功能涉及 3 个团队,我们要不要做?做了有什么坑?"

推荐组合:Superpowers brainstorming + what-could-break + before-you-build

实操步骤

Step 1 · 装所有"建前审查"skill

npx agentic-awesome-skills \
  --skills brainstorming,before-you-build,what-could-break,idea-autopsy

Step 2 · before-you-build(30 分钟)

> 用 before-you-build 审查答案溯源想法:
   - 需求验证:用户真的需要吗?
   - 替代方案:其他实现路径?
   - 切换成本:用户怎么迁移?
   - 渠道:怎么触达用户?

Step 3 · what-could-break(20 分钟)

> 用 what-could-break 评估爆炸半径:
   - 检索服务挂了怎么办?
   - 引用错位会怎样?
   - 性能影响?

Step 4 · brainstorming 跨团队讨论(1-2 小时)

> 拉 3 个团队的 Tech Lead 一起 brainstorming
   - 每个团队提 3 个"我们关心的问题"
   - brainstorming 自动组织讨论

Step 5 · 产出 RFC + spec-kit

基于以上发现,写 RFC 文档,跨团队评审,通过后用 spec-kit 拆 spec

🧪 场景 4:技术 POC 阶段

🧪 状态:技术可行性未知

典型表现:"我们不确定 RAG 检索能达到 95% 准确率,先验证一下"

推荐组合:brainstorming(POC 模式) + recursive-research + Marvin(可选)

实操步骤

Step 1 · 决定"spike"还是"项目"

> brainstorming:这是 spike(快速验证)
   还是项目(完整 SDD)?
   → 大多数 POC 是 spike

Step 2 · recursive-research 调研方案(1-2 天)

> 用 recursive-research 调研 RAG 检索的 5 个方案
   - BM25 传统
   - 向量检索(FAISS/Qdrant)
   - 混合检索
   - 排序学习
   - ReRank

Step 3 · 选 2-3 个方案做 POC(3-7 天)

不用走 spec-kit,直接写代码验证

Step 4 · POC 评估(1 天)

基于结果选 1 个方案,再走 spec-kit

Step 5 · 进入 spec-kit

> /speckit-specify RAG 检索功能
   (基于 POC 验证的方案)

关键:POC 阶段不要走 spec-kit(POC 不一定成)。brainstorming 明确区分"spike"和"项目"。

📑 场景 5:已有 PRD,直接拆 spec

📑 状态:PRD 完整,功能清晰

典型表现:"PM 已经把 PRD 写好了,我们直接拆 feature"

推荐组合:rich-elicitation(快速收边界) + 直接 spec-kit

实操步骤

Step 1 · 装 rich-elicitation

npx agentic-awesome-skills --skills rich-elicitation

Step 2 · rich-elicitation 扫 PRD(30 分钟)

> 用 rich-elicitation 扫 [粘贴 PRD 路径]:
   - 列出 5-10 个不清楚的点
   - 按优先级排序
   - 等你回答后,补充 spec 输入

Step 3 · 拆 feature 列表(1-2 小时)

用上一轮我们讨论的 5 步法 / 6 步实操法,拆出 feature 列表

Step 4 · 直接 /speckit-specify

> /speckit-specify 第一个 feature
> /speckit-specify 第二个 feature
...

关键:这种情况不需要重型发现工具,rich-elicitation + 5 步法就够。

⚠️ 选型常见错误

⚠️ 选型常见错误

错误后果正确做法
❌ 装太多 skill,挑花眼 2 周还在选,没开始 先装 1-2 个最常用,跑通再加
❌ 不评估项目状态直接选 用错工具,产出无效 先看决策树,定位项目状态
❌ 用 Kiro 但要切换 IDE 团队抵触,推不动 已经在 Claude Code 生态,选 Superpowers / OpenSpec
❌ 选了发现工具但跳过 spec-kit 产出无结构化,无法 Converge 发现阶段 → spec-kit 是连续流程
❌ POC 阶段走 spec-kit POC 失败,白写 spec POC 阶段用 brainstorming + recursive-research
❌ 用 Marvin 写非 Python 项目 不匹配 非 Python 项目用 OpenSpec / Superpowers

✅ 选型检查清单

✅ 选型检查清单

选型前 3 个核心问题

  • Q1. 我的项目状态是 5 种场景中的哪个?
  • Q2. 我在哪个 IDE?(Claude Code / Kiro / 其他)
  • Q3. 团队/个人使用?(影响学习曲线容忍度)

实操前 3 个准备

  • 准备 1 段自然语言描述(2-5 句)
  • 决定装 1 个还是多个工具
  • 决定安装路径(全局 vs 项目级)

验证选型正确 3 个信号

  • 跑 1 次能产出可用的"发现输出"(design doc / feature 列表)
  • 输出能直接作为 /speckit-specify 的输入
  • 团队成员都能用(学习曲线可接受)

需要切换工具的 3 个信号

  • 用 1 周后,产出的 spec 质量反而更差
  • 团队成员抱怨"太复杂了"
  • 工具的输出与 spec-kit 格式冲突

关键总结:

  1. 本项目 80% 情况不需要额外发现工具(已有 RFC + Constitution)
  2. 推荐默认方案:spec-kit + Superpowers(brainstorming 按需启用)
  3. 决策树:用图 2 的 4 个分支(🅰️🅲️🅴️🅵️)快速定位
  4. 5 个场景:分别有对应工具组合,直接套用
  5. 安装时间:5-10 分钟即可上手

下一步建议:

  1. 今天就试用 Superpowers brainstorming(5 分钟)
  2. 下次遇到模糊需求时,先走决策树再选工具
  3. 如果想用 OpenSpec,先在小项目验证
  4. 需要我帮你针对你的下一个 feature演示一遍"决策树 → 选工具 → 产出 → 接入 spec-kit"的完整流程吗?
