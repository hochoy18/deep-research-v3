🧬 本质:从自然语言到结构化 spec

/speckit-specify 的 SKILL.md metadata 给出了明确定义:

---
name: "speckit-specify"
description: "Create or update the feature specification from a
             natural language feature description."
argument-hint: "Describe the feature you want to specify"
compatibility: "Requires spec-kit project structure with .specify/ directory"
metadata:
  author: "github-spec-kit"
  source: "templates/commands/specify.md"
user-invocable: true
disable-model-invocation: false
---

三个关键属性

属性值含义
description "Create or update the feature specification from a natural language feature description" 输入只能是"自然语言描述",不接受结构化参数
argument-hint "Describe the feature you want to specify" 提示用户用自然语言描述功能
user-invocable true 用户可在 Claude Code 输入框直接调用

它在 Spec Kit 流程链中的位置

图 1:specify 在流程链中的位置——承接宪法,产出 spec,被 clarify/plan/tasks 消费

硬规则(SKILL.md 行 111):

"You must only create one feature per /speckit-specify invocation"

一次调用 = 一个 feature。批量创建多个 feature 是违规。

📝 natural language feature description 参数详解

这是 SKILL.md argument-hint 字段定义的唯一输入参数。注意:

SKILL.md 行 16-20:

## User Input

```text
$ARGUMENTS
```

You **MUST** consider the user input before proceeding (if not empty).

且行 121:"If empty: ERROR 'No feature description provided'"

这个参数的 5 个硬性约束

#约束SKILL.md 引用违反后果
1 必须非空 行 121 直接报错,完全不执行
2 必须是自然语言 行 3-4 "natural language feature description" 不是 JSON / YAML,不能是结构化参数
3 粒度可变 行 60 "The text the user typed... is the feature description" 可短可长,Agent 会适配
4 每次只描述 1 个 feature 行 111 "one feature per invocation" 多 feature 拆多次调用
5 可含技术术语 行 68 "Preserve technical terms and acronyms (OAuth2, API, JWT)" 但"避免 HOW 实现细节"

🎚️ 输入的 6 种粒度

基于 SKILL.md 真实工作流,自然语言输入的粒度决定 Agent 走哪条路。这是用户最需要掌握的实操技巧。

粒度 1:具体场景(20-50 字)

推荐度:⭐⭐⭐⭐⭐

示例:

给已登录用户,首页底部展示"看了又看"列表,最多 5 条,基于最近 7 天浏览历史

Agent 行为:直接生成完整 spec,基本无 [NEEDS CLARIFICATION]

粒度 2:用户故事(50-200 字)

推荐度:⭐⭐⭐⭐⭐

示例:

作为已登录用户,
我想看到"看了又看"推荐列表,
以便发现我可能感兴趣的内容。

列表:最多 5 条;
排序:基于浏览历史;
位置:首页底部;
数据:最近 7 天;
不做:不实时,每天 1 次离线

Agent 行为:1-2 个澄清问题,然后生成

粒度 3:产品需求(200-500 字)

推荐度:⭐⭐⭐⭐

示例:

需求背景:提升首页停留时长
用户痛点:用户不知该看什么
目标:KPI 提升 20%
功能:推荐 5 条相似内容
约束:每天 1 次离线更新
不做:不做协同过滤,不做个性化排序

Agent 行为:大量推断 + 关键澄清(2-3 个)

粒度 4:RFC 摘要(500-2000 字)

推荐度:⭐⭐⭐

示例:把整个 RFC 文档贴进来

Agent 行为:信息充足但需裁剪,只取 1 个 feature 范围

风险:信息过载,可能误解为多个 feature

粒度 5:模糊想法(1-2 句)

推荐度:⭐⭐(不推荐)

示例:

做个推荐系统

Agent 行为:3 个 [NEEDS CLARIFICATION] 全用上

风险:澄清完后 spec 还是粗糙

粒度 6:技术方案(避开)

推荐度:❌(违反原则)

示例:

用 FAISS 向量库 + Redis 缓存
加 Python 异步任务 + React 组件

问题:SKILL.md 行 285-288 明文要求"Avoid HOW to implement"

Agent 行为:提取业务需求,忽略技术细节

实操建议(本项目场景):

推荐粒度 2(用户故事)或粒度 3(产品需求)。这两个粒度:

  • ✅ 信息足以让 Agent 生成完整 spec
  • ✅ 留有 1-3 个澄清空间,Owner 主动决策
  • ✅ 符合宪法 "WHAT not HOW" 要求

📁 目录与编号系统

SKILL.md 行 86-94 详细定义了 spec 目录的解析规则。理解这一点对多 feature 并行很重要。

两种编号方案

feature_numbering目录格式示例优缺点
"sequential"(本项目) NNN-<short-name> 003-user-auth ✅ 编号紧凑,容易排序
❌ 多人同时创建可能冲突
"timestamp" YYYYMMDD-HHMMSS-<short-name> 20260319-143022-user-auth ✅ 全球唯一,无冲突
❌ 编号长,不易记忆

概念类型说明示例

❓ [NEEDS CLARIFICATION] 决策

SKILL.md 行 125-131 是specify 最巧妙的设计之一——Agent 不会"硬问"所有不清楚的事,而是按优先级决定:先推断、再标注、最后问。

图 5:Agent 遇到不清楚细节时的决策树——首选默认,次选标 [NEEDS CLARIFICATION],最后问

SKILL.md 行 308-319 给出的"合理默认"清单

领域默认(不需问)
数据保留用行业标准
性能目标用标准 Web/移动 App 期望
错误处理用户友好提示 + 合理 fallback
认证方式Web 用 session 或 OAuth2
集成模式Web 用 REST/GraphQL;库用函数调用;工具用 CLI

需要 [NEEDS CLARIFICATION] 的场景(SKILL.md 行 125-127)

  • 选择会显著影响 scope 或 UX
  • 存在多种合理解释且影响不同
  • 没有任何合理默认

澄清问题格式(SKILL.md 行 206-223)

## Question [N]: [Topic]

**Context**: [引用 spec 相关段落]

**What we need to know**: [具体问题]

**Suggested Answers**:

| Option | Answer | Implications |
|--------|--------|--------------|
| A      | 第一种建议 | 对功能的影响 |
| B      | 第二种建议 | 对功能的影响 |
| C      | 第三种建议 | 对功能的影响 |
| Custom | 自己提供答案 | 如何给 |

**Your choice**: _[等待用户回答]_

硬规则(SKILL.md 行 130):

"LIMIT: Maximum 3 [NEEDS CLARIFICATION] markers total"

超过 3 个时,按"scope > security/privacy > UX > technical details"优先级,只保留前 3 个,其余用"informed guess"。

📋 9 个 Section 模板

spec-template.md 规定 6 个必填 + 3 个可选 Section(SKILL.md 行 290-294)。

必填(必须完成)

#Section作用填写要求
1 User Scenarios & Testing 用户场景 + 验收测试 必须有 primary user story;无流程则报错(SKILL.md 行 133)
2 Requirements 功能需求(Functional Requirements) 每条 MUST 可测试(SKILL.md 行 135);用 MUST/SHOULD/MAY 开头
3 Key Entities 关键实体(如涉及数据) 列出主要数据对象
4 Success Criteria 成功标准 可衡量、技术无关(SKILL.md 行 136-139)
5 Assumptions 假设(Agent 的推断) 把 informed guesses 写在这里
6 Edge Cases 边缘情况 列出极端情况与处理方式

可选(相关时填,不相关删除整个 Section,不留 N/A)

#Section何时需要
7Dependencies有外部依赖时
8Out of Scope边界模糊时明确"不做"
9Open QuestionsClarify 阶段前的暂存区

SKILL.md 行 294 关键提示:

"When a section doesn't apply, remove it entirely (don't leave as 'N/A')"

不相关的 Section 要整个删除,不能留 "N/A" 占位。

📘 本项目案例:RFC-002 → FEATURE-007

本项目有一个 RFC-002 答案溯源 的全景设计,这是用 specify 第一个可执行的子 feature 的真实过程。

RFC-002 拆解

RFC-002 答案溯源(Accepted)
├── FEATURE-007: 片段 ID 生成器(本次 specify)
├── FEATURE-008: 引用映射插入
├── FEATURE-009: 引用渲染组件
└── FEATURE-010: 跳转交互

用户输入(natural language,粒度 2)

/speckit-specify 实现片段 ID 生成器:

作为检索服务,
我想为每个返回的检索片段打一个唯一 ID 并持久化,
以便后续引用映射能定位到原始片段。

输入:检索结果(标题、URL、摘要、来源)
输出:每个片段带 ID 字段
存储:用现有 PostgreSQL,新增 fragments 表
不做:不做向量化,不做 embedding 索引,不做缓存层

性能:10,000 片段/秒写入
一致性:写入失败必须报错,不能丢

Agent 提取的关键概念

Actors:    [检索服务,后续引用服务(下游)]
Actions:   [生成 ID, 持久化片段, 返回带 ID 的结果]
Data:      [片段(标题、URL、摘要、来源、ID)]
Constraints: [PostgreSQL 持久化, 10K 写入/秒, 失败报错不丢]

生成的 spec.md(本项目 007 样例)

# Feature Specification: 片段 ID 生成器

**Feature ID**: FEATURE-007-fragment-id
**Owner**: @zhang-san(检索团队)
**Status**: Draft
**Created**: 2026-10-14

## User Scenarios & Testing

### Primary User Story
**As a** 检索服务
**I want to** 为每个返回的检索片段打一个唯一 ID 并持久化
**So that** 后续引用映射能定位到原始片段(为答案溯源功能打底)

**Acceptance Scenarios**:

1. **Given** 检索服务返回 1 个检索结果(标题/URL/摘要/来源)
   **When** 调用片段 ID 生成器
   **Then** 该片段获得唯一 ID(UUID v7),并持久化到 fragments 表
   **And** 返回的检索结果中该片段带 `id` 字段

2. **Given** 同一 URL/标题/摘要的片段已经存在
   **When** 再次调用
   **Then** 返回已有的 ID(幂等)

3. **Given** 数据库写入失败
   **When** 调用片段 ID 生成器
   **Then** 返回 500 错误,且不返回部分结果

### Edge Cases

- 检索结果中 URL 缺失或无效:拒绝处理,返回 400
- 同一秒内 10,000+ 片段:无 ID 冲突(PK 约束保证)
- 数据库连接断开:重试 3 次后失败报错

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 为每个检索片段生成 UUID v7 作为唯一 ID
- **FR-002**: 系统 MUST 在 fragments 表持久化(URL、标题、摘要、来源、ID、created_at)
- **FR-003**: 系统 MUST 支持幂等性:同一 URL/标题/摘要返回相同 ID
- **FR-004**: 系统 MUST 在写入失败时返回错误,不返回部分结果
- **FR-005**: 系统 MUST 在检索结果中返回带 `id` 字段的片段

### Non-Functional Requirements

- **NFR-001**: 吞吐量 MUST ≥ 10,000 片段/秒
- **NFR-002**: P99 延迟 MUST ≤ 50ms(不含网络)
- **NFR-003**: ID 生成 MUST 符合 RFC 9562(UUID v7)

## Key Entities

- **Fragment(片段)**:
  - `id`: UUID v7,主键
  - `url`: 文本,NOT NULL,索引
  - `title`: 文本,NOT NULL
  - `snippet`: 文本,NOT NULL
  - `source`: 文本(检索来源标识)
  - `created_at`: TIMESTAMP,NOT NULL,默认 NOW()

## Success Criteria

- **SC-001**: 检索服务能以 10,000 片段/秒的速度通过本服务
- **SC-002**: 100% 写入失败能被上游捕获并重试
- **SC-003**: 重复片段(同 URL+title+snippet)始终返回相同 ID
- **SC-004**: 检索结果 100% 带 `id` 字段
- **SC-005**: 数据保留期 ≥ 90 天(支持事后追溯)

## Assumptions

- 现有 PostgreSQL 实例可承载新增表(容量评估见 RFC-002 第 5.3 节)
- UUID v7 满足唯一性要求(冲突概率 < 10^-9)
- "幂等"定义基于 URL+title+snippet 三元组哈希(由 Owner 确认)
- 检索结果单批最大 1000 片段(由调用方约束)

## Out of Scope

- 不做向量化(由 FEATURE-012 单独 spec)
- 不做 embedding 索引
- 不做片段缓存层
- 不做跨团队数据同步
- 不做片段去重(只在片段 ID 层面)

## Dependencies

- PostgreSQL 14+(已在生产)
- 检索服务上游(由检索团队维护)
- 引用服务下游(FEATURE-008 尚未开始)
