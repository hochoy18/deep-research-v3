🧬 本质:宪法 + 智能填表工具

/speckit-constitution 不是普通 slash command,而是一个 Agent Skill。SKILL.md 的 metadata 给出了明确定义:

---
name: "speckit-constitution"
description: "Create or update the project constitution from interactive or provided principle inputs."
argument-hint: "Principles or values for the project constitution"
compatibility: "Requires spec-kit project structure with .specify/ directory"
metadata:
  author: "github-spec-kit"
  source: "templates/commands/constitution.md"
user-invocable: true
disable-model-invocation: false
---

三个关键属性

属性值含义
description "Create or update the project constitution from interactive or provided principle inputs" 支持两种输入模式:对话式交互 或 一次性提供
argument-hint "Principles or values for the project constitution" 输入框提示用户输入"原则或价值观"
user-invocable true 用户可在 Claude Code 输入框直接调用

🚧 Scope Guard:权限边界

SKILL.md 第 22-39 行的 Scope Guard 是整个 Skill 最关键的安全设计,容易被忽视:

Scope Guard 原文(行 22-39):

This command's own work is limited to updating the project constitution itself. Dependent templates and commands read the constitution at runtime and are not modified here.

  • If the input includes feature implementation, code generation, refactoring, building, or deployment requests, you MUST NOT execute them. Extract them as deferred intents instead.
  • You MUST NOT create, modify, or delete application source files, feature routes, components, tests, deployment files, or other artifacts unrelated to the constitution workflow.
  • If it is unclear whether an instruction is constitution content, ask for clarification before making changes.
  • After completing the constitution update, include a Next Actions section for each deferred intent.
图 5:Scope Guard 分流——治理内容直接处理,非治理内容提取为 deferred intent

3 个典型 Scope Guard 触发场景

你的输入Scope Guard 怎么处理
/speckit-constitution 我们要做答案溯源功能,每段加 [n] 引用 "答案溯源"是 feature 实现,提取为 deferred intent。Next Actions 建议 /speckit-specify。
/speckit-constitution 加 Security-First 原则,另外帮我把 src/auth/ 重构一下 "加原则"做,"重构 src/auth/"提取为 deferred intent,绝不会执行。
/speckit-constitution 把 Security-First 改为"用 OAuth2" 不清楚是治理还是技术决策 → AskUserQuestion 弹出让你澄清。

🔄 Interactive vs Provided 模式

SKILL.md 的 description 明文提到两种输入模式:interactive(对话式) 和 provided(一次性提供)。两种模式对应不同的使用场景。

🅰️ Interactive 模式(对话式)

用法:只输入 /speckit-constitution(不带详细参数),让 Agent 主动问。

流程:

  1. 你: /speckit-constitution
  2. Agent: 你这个项目的核心原则是什么?(弹出 AskUserQuestion)
  3. 你: Security、Test-First、Simplicity
  4. Agent: 测试覆盖率指标?(弹出 AskUserQuestion)
  5. 你: 关键路径 ≥80%
  6. ... 继续澄清直到 Agent 有足够信息
  7. Agent: 生成 constitution.md

适用场景:

  • ✅ 项目想法还很模糊,需要引导
  • ✅ 第一次创建宪法,不知道 spec-kit 该要什么
  • ✅ 想让 Agent 帮你"激活思路"
  • ✅ 团队工作坊:集体讨论时用

注意事项:

  • ⚠ Agent 问的每个问题要回答,不能跳过
  • ⚠ 整个过程可能 5-15 分钟(取决于问题数)
  • ⚠ Agent 可能用 LLM 默认假设填充你没明说的细节

🅱️ Provided 模式(一次性提供)

用法:输入 /speckit-constitution [完整描述],Agent 一次性处理。

流程:

  1. 你: 准备一份 200-2000 字的 principle inputs(含 4 部分)
  2. 你: /speckit-constitution [粘贴整段]
  3. Agent: 解析、映射、推断缺失值、校验、生成
  4. Agent: 输出摘要(含 TODO 项让你后续补)
  5. 你: Review,改 TODO 项,提交 PR

适用场景:

  • ✅ 已经开过 Constitution Workshop,有现成原则
  • ✅ 从已有 v1.0.0 升级到 v1.1.0,有明确变更清单
  • ✅ 团队已有 engineering playbook,只需要"翻译"成宪法格式
  • ✅ 想要"白纸黑字"留底,避免被 Agent 假设污染

注意事项:

  • ⚠ 占位符必须显式给(尤其是 [PROJECT_NAME]、[GOVERNANCE_RULES])
  • ⚠ 太短(<200 字)会被 Agent 大量推断,产出偏通用
  • ⚠ 太长(>3000 字)Agent 抓不住重点
图 7:两种输入模式的时序对比——Interactive 是"逐步问答",Provided 是"一次性处理"

⭐ 5 个质量维度

每条原则都应该满足 SKILL.md 第 127 行 Validation 要求的 5 个标准:

#维度校验问题反例正例
1 强约束词 是否 MUST/SHALL/SHOULD NOT 开头? "尽量做测试" "PR MUST 通过关键路径覆盖率 ≥80%"
2 可测试 是否能转成 CI 门禁? "代码要优雅" "PR MUST 引用至少 1 个 spec ID"
3 项目级 适用所有 feature 吗? "所有支付模块..." "所有外部输入..."
4 持久性 项目生命周期内成立吗? "用 React 18.2" "SAST/SCA 强制门禁"
5 无 [ALL_CAPS] 残留 所有占位符都填了? 留有 [PROJECT_NAME] 全部填入具体值

真实的 Sync Impact Report

这是 v1.1.0 文件顶部的 HTML 注释(实际内容,来自项目当前 constitution.md):

从 v1.0.0 升级到 v1.1.0 用的 prompt(推测的 Provided 模式)

/speckit-constitution 基于现有 v1.0.0 升级:

【新增原则】(让 3 团队协作真正可追溯 / 收敛 / 责任明确)
- II. Spec-Traceable:
  规则:每个 PR MUST 引用一个 spec ID
  细则:spec ID 由 /speckit-specify 产出,格式 FEATURE-NNN-slug;
       PR 模板必填 Spec: 字段;hotfix 例外但 5 工作日内补建
  理由:3 团队并行迭代,无追溯会出现"实现了谁的需求"责任真空

- IV. Converge-Gate:
  规则:任何 feature MUST Converged 才能合并到 main/release/*
  细则:spec/plan/tasks 齐备 + checklist 全过 + analyze/converge 无未对齐项 +
       CI 关键路径 ≥80%/SAST-SCA/Pact/性能基准全过
  理由:多团队无收敛门禁会有"看起来做完了实际未对齐"的技术债

- V. One-Feature-Owner:
  规则:每 feature 有且仅有一个 Owner
  细则:Owner 负业务决策+跨团队沟通+Converge 报告+事后复盘;Co-Owner 不担责
  理由:多人负责=无人负责;责任显式落到个人

【强化原则】
- I. Security-First:
  加 SAST/SCA 强制门禁(高危阻断、中危 7 天修复、人工豁免需 Security Owner 批准)

- III. Test-First (NON-NEGOTIABLE):
  收口覆盖率指标:从"单元测试 ≥80%"改为"关键路径 ≥80%"
  关键路径定义:检索→过滤→推理→生成 / 鉴权 / 状态机 / 外部 API / 持久化

【保留不动】
- Performance Standards / Compliance / Development Workflow / Governance

v1.1.0 产出的核心原则全貌

I

Security-First(强化)

外部输入白名单 + 服务端鉴权 + 审计三元组 + SAST/SCA 强制门禁

每个 PR MUST 引用 spec ID(FEATURE-NNN-slug)

OpenAPI + Pact + Controller 薄

可观测性默认

结构化 JSON 日志 + Prometheus + OpenTelemetry

VIII

📋 Sync Impact Report 详解

SKILL.md 第 114-121 行描述了 Sync Impact Report 的生成规则,但最容易被误解的是它的"临时性":

SKILL.md 原文(行 115-116):

"This report is temporary scratch material for human review of the amendment, not governance content; it is expected to be removed before the amended constitution file is committed."

翻译:Sync Impact Report 是临时审阅材料,不是治理内容;预期在 commit 前删除。

Report 必须包含的 5 项内容

项目示例

Modified principlesI. Security-First (强化: 新增 SAST/SCA)
Added sectionsCI Gates 章节新增 Spec-Trace / Converge-Gate 校验
Removed sections(修订场景,如有)
Follow-up TODOs未填的占位符、延迟项、需人工确认的歧义

RATIFICATION_DATE = 原始采纳日期(修订时保持原值,不知道就 TODO) LAST_AMENDED_DATE = 今日(改了的话)/ 保持前值(没改的话)

⚖️ Governance 必备 3 项

SKILL.md 第 112 行明确 Governance 章节必须包含:修订流程 + 版本策略 + 合规审查期望。本项目 v1.1.0 的 Governance 章节做到了这 3 项 + 一个加分的运行时指引:

必备项v1.1.0 实际内容关键约束
修订流程 提案 → 评审 → 批准 → 公告 → 版本号 → 生效(6 步) Tech Lead Council 过半数批准;Sync Impact Report 必填
版本策略 MAJOR/MINOR/PATCH 3 级 SemVer,带具体定义 SKILL.md 第 103-105 行明文要求
合规审查 PR/Code Review/发布流程 MUST 校验合规;复杂度 MUST 在 PR 中显式说明 "违规 MUST 在 CI 被拦截,不得人工豁免"
运行时指引(加分项) 指向 docs/dx/、reference/validation、docs/governance/constitution-changelog.md 让宪法"可被查阅",不止是挂在文件里的规则

反例:Governance 章节缺失的常见问题

  • ❌ 只写修订流程不写违规后果 → 原则变成"软约束"
  • ❌ 只写违规后果不写修订流程 → 宪法成"死规则",无法演化
  • ❌ 修订条款写"由 Owner 决定" → 没有制衡机制
  • ❌ 不指向运行时文档 → 团队新人不知道去哪查细节

🛠️ 标准执行流程

基于 SKILL.md 真实工作流 + 本项目状态,推荐的标准执行流程:

Step 1 · 准备输入(Provided 模式)

准备 principle inputs:200-2000 字,含 4 部分(项目背景 / 核心原则 / 附加章节 / Governance)。

Step 2 · 启动 Claude Code,执行命令

cd /Users/cai.he/.../deep-research/v3
claude
# 在 Claude Code 输入框:
/speckit-constitution [粘贴整段 principle inputs]

Step 3 · Agent 执行 7 步

观察 Agent 工具调用进度(Read 模板 → Reason 解析 → Write 文件)。如有 AskUserQuestion 弹出,逐个回答。

Step 4 · Review 5 条 Validation

Agent 会自己跑一遍 Validation,你需要再人工 review:占位符填全 / MUST 开头 / 每条 ≤3 行 / Governance 3 必备项 / 日期 ISO。

Step 5 · 处理 Sync Impact Report

查看 Agent 生成的 HTML 注释:commit 前删除(或保留作为 changelog)。

Step 6 · 创建 PR

本项目要求 1 个跨团队 reviewer + Converge 报告(根据 Converge-Gate 原则)。建议 commit message:

docs(constitution): amend to v1.2.0 (principle additions)

- 新增 IX. Anti-Hallucination
- 强化 III. Test-First 关键路径
- Tech Lead Council 过半数批准
- 迁移计划:见 docs/governance/v1.2.0-migration.md

Step 7 · 同步公告

合并后按 Governance 要求:同步公告 3 个团队 + 归档到 docs/governance/constitution-changelog.md。

✅ 实操检查清单

执行命令前

  • 确认 .specify/ 已初始化(spec-kit 已安装)
  • 决定模式:Interactive(让 Agent 引导)或 Provided(自己准备)
  • Provided 模式:准备好 200-2000 字 principle inputs,含 4 部分
  • 确认要创建(首次)还是修订(已有宪法)
  • 修订场景:明确变更清单(新增/强化/删除)

执行命令中

  • 启动 Claude Code,在项目根目录执行
  • 监控 Agent 工具调用进度
  • 认真回答每个 AskUserQuestion 弹窗
  • 看到"完成报告"后不要急着走

Review 阶段

  • PROJECT_NAME 填了,不是 TODO
  • 所有 [ALL_CAPS] 占位符已替换
  • 每条原则 MUST/SHALL 开头
  • 每条原则 ≤3 行
  • 版本号正确(SemVer 规则)
  • 日期 ISO 格式(YYYY-MM-DD)

  • 违规后果条款明确
  • 运行时指引指向具体文档
