团队协作实战方案

用 Spec Kit 协作开发一个真实项目:分工 / 分支 / 门禁 / 节奏,一文讲透。

5–20 人团队 可直接落地 含 CI 模板

🏛️ 协作模型总览

假设团队规模 5–20 人,正在做一个中大型项目。核心思路是 "状态隔离 + 阶段门禁 + Review 闭环"。

🎬 阶段 0 · 团队初始化(项目第 1 天)

0.1 仓库初始化

Lead 执行:

# 1. 安装 CLI
uv tool install specify-cli

# 2. 创建项目(一次性,非交互)
specify init my-platform --integration copilot --non-interactive

# 3. 关联远程仓库
git init
git remote add origin <team-repo-url>
git push -u origin main

0.2 制定 Constitution(宪法)

在 Copilot 中执行:

/speckit-constitution

并写入项目的指导原则,例如:

  1. Security-First:任何 PR 必须通过 SAST/SCA
  2. Spec-Traceable:每个 PR 必须引用一个 spec ID
  3. Test-First:关键路径测试覆盖率 ≥ 80%
  4. Converge-Gate:任何 feature 必须 Converged 才能合并
  5. One-Feature-Owner:每个特性有且仅有一个 Owner

产出:.specify/memory/constitution.md —— 必须提交到 Git,所有人均可访问。

0.3 仓库目录结构

0.4 分工策略 — 按特性切片(非角色分层)

模式组成优缺点
❌ 按角色分层 前端 3 人 / 后端 3 人 / 测试 1 人 前端等后端接口,后端等前端确认 — 串行等待
✅ 按特性切片
(推荐)		 每特性 1 Owner + 1–2 开发者 端到端负责,前后端都写 — 反馈环最短
🎯 核心建议

每个特性独立运行完整 9 步,团队成员拥有完整上下文。Lead 负责仲裁与 Review,不参与具体实现。

🔧 阶段 1 · 协作核心机制

1.1 特性目录与状态隔离

每个特性一个独立目录,通过 .specify/feature.json 切换上下文:

# 张三做特性 002
echo '{"feature": "002-task-board"}' > .specify/feature.json
# 之后所有 /speckit-* 命令都基于这个目录

# 王五做特性 003(切换上下文)
echo '{"feature": "003-notifications"}' > .specify/feature.json
💡 隔离的三个好处
  • 多人同时操作不同特性,互不干扰
  • 即使两个特性改动同一文件,合并时是 spec 级别的冲突(可读、可解决)
  • feature.json 可加入 .gitignore,或团队约定提交时忽略

📅 阶段 2 · 9 步协作示例

假设张三和李四协作做特性 002-task-board:

📝 Day 1 — 张三:启动特性

git checkout -b 002-task-board
echo '{"feature": "002-task-board"}' > .specify/feature.json

# 在 Copilot 中
/speckit-specify "Taskify 的任务看板:用户可以创建任务、分配、拖拽改状态,实时多人协作"

产出:features/002-task-board/spec.md

❓ Day 1 — 李四:协同澄清

git pull && git checkout 002-task-board

# 自己的 Copilot
/speckit-clarify
# AI 问:"实时协作意味着 WebSocket 还是短轮询?"
# 李四回答 → 自动合并到 spec.md

git add . && git commit -m "clarify:明确实时协作采用 WebSocket"
git push

🤝 协作要点:spec.md 是共享资产,任何人都可以补充,但每次修改要 commit message 清晰。

🏛️ Day 2 — 张三:制定方案

/speckit-plan
# 输入:PostgreSQL + Node.js + Socket.io + React

产出:plan.md(技术方案 + 架构 + 权衡)

✅ Day 2 — 李四:质量 checklist

/speckit-checklist
# AI 生成"需求质量检查清单"
# 李四逐项核对,勾选已满足的项

产出:checklists/requirements.md(可勾选)

📋 Day 3 — 张三:拆解任务

/speckit-tasks
# 自动产出按依赖排序的 tasks.md

关键设计:[P] 表示可并行,[US1] 表示关联用户故事 —— 任务有了"故事标签"和"并行标签"。

🔍 Day 3 — Lead 介入:analyze 一致性

# Lead 切到该特性
echo '{"feature": "002-task-board"}' > .specify/feature.json
/speckit-analyze
# 输出:跨 spec/plan/tasks 的一致性报告
⚠️ Review 核心节点

Lead 在这一步介入,而不是等代码写完才发现问题。

⚒️ Day 4–7 — 张三、李四并行实现

# 张三做 T01、T02(后端)
/speckit-implement --filter T01,T02

# 李四做 T04(前端)
/speckit-implement --filter T04

关键:tasks.md 中的 [P] 标签让 AI 知道哪些可并行,团队成员各自实现自己的子集。

🎯 Day 8 — 张三:收敛验证

/speckit-converge
# 输出:"Converged" 或 "需要追加以下任务..."

# 如果追加了任务,继续
/speckit-implement
/speckit-converge
# 直到 Converged

🚢 Day 9 — Lead:合并

git checkout main
git merge --no-ff 002-task-board -m "feat: 002-task-board 完成"
git push

# 归档特性
mv features/002-task-board specs/

3.2 PR Review Checklist

团队应维护一份**统一的 Review 清单**,每个 PR 都按它走:

## PR Review Checklist
- [ ] 该 PR 引用的 spec.md 存在且已合并
- [ ] tasks.md 中对应任务被勾选
- [ ] /speckit-analyze 无报告
- [ ] 测试覆盖率 ≥ 80%
- [ ] /speckit-converge 输出 Converged
- [ ] Constitution 中的相关原则已遵守

3.3 CI/CD 集成(企业级)

将 Spec Kit 接到 CI,作为合并硬性条件:

# .github/workflows/spec-kit-ci.yml
name: Spec Kit CI
on: [pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 1. 验证 PR 引用的 spec.md 存在
      - name: Check spec reference
        run: |
          if ! grep -r "spec.md" .specify/; then
            echo "::error::PR 必须引用 spec.md"
            exit 1
          fi

      # 2. 运行 /speckit-analyze
      - name: Run analyze
        run: |
          uv tool run specify-cli analyze

      # 3. 验证 checklist 完整性
      - name: Check checklist
        run: |
          python .specify/scripts/check_checklist.py

👥 阶段 4 · 角色与权限

角色人数职责
👑 Lead / Architect1维护 constitution、最终 merge 仲裁
🔍 Tech Reviewer1–2跑 /speckit-analyze、审核 plan.md
🎯 特性负责人每特性 1跑 /speckit-specify、拆任务、协调
💻 特性开发者每特性 1–3实现 tasks.md 中的子集
🧪 QA1跑 /speckit-converge、补充 checklist

📆 阶段 5 · 日常节奏建议

每日站会(15 分钟)

  • 昨天跑了哪个 /speckit-* skill?
  • spec.md / plan.md / tasks.md 是否更新?
  • 卡点是什么(技术 / 规格 / 资源)?

每周 Spec Review(Lead 主持)

  • 本周合并的 spec.md 质量如何?
  • Constitution 是否需要更新?
  • 哪些流程节点耗时过长?

每月 Retro

  • /speckit-converge 平均几次能 Converged?
  • 哪些步骤经常跳行?(通常是 constitution 不完善)
  • 是否需要新增 extension / preset?

⚠️ 阶段 6 · 常见坑 & 防范

坑表现防范
跳过 constitution每个特性风格漂移项目第一天 Lead 强制运行
跳过 clarify实现到一半 spec 被重定义任何超过 3 天的特性都跑
跳过 checklist临交付发现需求缺口接进 CI,作为合并条件
跳过 analyze多人合并时大量冲突Lead 在合并前必跑
converge 反复失败spec/实现对不上constitution 明确"每次失败追加任务,不许删任务"
特性目录混乱找不到当前激活特性.specify/feature.json 必须反映现实,Lead 抽查
同特性多人同时改 spec.md互相覆盖用分支 + PR,不在 main 上直接改

🚀 阶段 7 · 实战启动脚本

在 organization-sh.md(团队首个文档)写入:

# 团队使用规范

## 工作流
每个特性必须走完整 9 步:
constitution(项目级一次) → specify → clarify →
plan → checklist → tasks → analyze →
implement → converge

## 分支策略
- 主分支:main(受保护,需 PR +1 Review)
- 特性分支:NNN-feature-name
- 归档:合并后 mv 到 specs/NNN-dir/

## Review Gate(PR 必须满足)
1. 引用 spec.md 路径
2. /speckit-analyze 无错
3. /speckit-converge 输出 Converged

## 角色
(按团队实际填写)

## 工具
- AI 智能体:Copilot(配 Claude API)
- CLI:specify-cli vX.Y
- CI:GitHub Actions(spec-kit-ci.yml)

📌 总结

🎓 核心三句话
  • 状态隔离:feature.json + 特性目录 = 每个成员在不同"沙箱"工作
  • 阶段门禁:每个 /speckit-* 都是质量门,跳步意味着债务
  • Review 闭环:Lead 在 analyze / merge 介入,不在代码写完后才介入
🌟 一句话

"规格是 AI 的共同记忆,也是团队共同的契约。"
