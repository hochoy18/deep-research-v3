Spec-Driven Development 快速入门

9 步走通一个完整特性:从 constitution 到 converge。

quickstart 翻译 9 步流程 含可读示例

📜 quickstart 页翻译与简介

本指南帮助你使用 Spec Kit 开启规格驱动开发。整个过程用一个持续演进的示例 Taskify(小型团队生产力平台)进行演示。

ℹ️ 关于流程独立性

使用 SDD 从规格构建特性或应用。若要修复缺陷,参考 Bug 修复流程;若要判断想法是否值得投入,参考想法评估流程。这些是独立流程,不是本指南的前置依赖。

💡 关于脚本与命令调用

自动化脚本同时提供 Bash(`.sh`)、PowerShell(`.ps1`)和 Python(`.py`)三种版本。交互式 specify init 会提示你选择;非交互模式(没有 TTY 或带 --non-interactive)默认按当前操作系统选 shell 版本。可以用 --script sh|ps|py 显式指定。

本流程的步骤基于 GitHub Copilot 的默认 skills 模式(/speckit-*)。在你的智能体聊天中,逐个调用每个 skill,并在进入下一步前先 review 产出结果。

🧠 上下文感知关键点

Spec Kit 通过 .specify/feature.json 中记录的 feature 目录来识别当前激活特性(可用 SPECIFY_FEATURE_DIRECTORY 环境变量覆盖)。命令解析的 feature 来自这个状态,而非 Git 当前分支 —— 不需要 Git。

可选的 git 扩展会增加编号命名的功能分支用于组织版本控制,但"激活特性"仍取决于状态文件所指向的目录。要切换特性,请更新 .specify/feature.json。

🛤️ 两条推荐路径

无论哪条路径,在项目开始前先建立 constitution(宪法)。

📥 安装 Specify

# 安装 CLI(基于 uv)
uv tool install specify-cli

# 初始化项目
specify init taskify --integration copilot

# 进入项目
cd taskify

init 可交互式选择编码智能体,也可用 --integration 显式指定。CI 和 AI agent harness 场景请加 --non-interactive。

📚 如偏好 pipx、一次性 uvx 运行或离线安装,参考 安装指南。把 Spec Kit 加入既有仓库请参考 既有项目中采用 Spec Kit。

🔁 完整 9 步流程图

📋 每步详解

Step 1 · /speckit-constitution — 设定基本规则

建立项目的指导原则(guiding principles)。项目开始时运行一次,把你的原则作为参数传给它。

产出:.specify/memory/constitution.md(提交到 Git,所有人均需遵守)

Step 2 · /speckit-specify — 描述要构建什么

从自然语言描述创建特性规格。聚焦"做什么"和"为什么",不要纠结技术栈。

产出:features/NNN-feature/spec.md

Step 3 · /speckit-clarify — 消除歧义

针对规格中欠明确的地方,提出有针对性的问题,并把答案整合回规格。

💡 关键设计

AI 会主动反问你"实时协作意味着 WebSocket 还是短轮询?" —— 把模糊点变成可决策点。

Step 4 · /speckit-plan — 选择技术栈

基于规格生成设计产物。提供技术栈和架构选型(如 PostgreSQL + Node.js + React)。

产出:plan.md(技术方案、架构、权衡)

Step 5 · /speckit-checklist — 验证规格

生成定制的质量检查清单,确认规格在拆解任务前是完整、清晰、一致的。这些是由 review 负责人维护的"需求质量评审产物"。

产出:checklists/requirements.md(可勾选)

Step 6 · /speckit-tasks — 拆解任务

基于设计产物,产出按依赖顺序排列的可执行 tasks.md。

📌 任务标签解读
  • [P] 表示可并行的任务
  • [US1] 表示关联到某个用户故事
  • [US1,US3] 表示跨多个故事的任务
# tasks.md 示例片段
- [ ] T01 [P] [US1] 搭建 PostgreSQL Schema
- [ ] T02 [P] [US1] 实现 REST API:CRUD 任务
- [ ] T03 [US2] 集成 Socket.io 服务端
- [ ] T04 [P] [US2] 实现拖拽 UI 组件
- [ ] T05 [US3] 集成 Socket.io 客户端
- [ ] T06 [US1,US2,US3] 端到端测试

Step 7 · /speckit-analyze — 一致性检查

横跨 spec.md、plan.md、tasks.md 报告冲突、缺口和歧义。只读 —— 在源头修复后再次运行,再开始实现。

⚠️ Lead 介入节点

这是 Review 的核心节点:Lead 在这一步介入,而不是等代码写完才发现问题。

Step 8 · /speckit-implement — 执行实现

按 tasks.md 中的依赖顺序执行任务。会以 checklist 复选框的状态作为门禁(未勾上的不能继续)。

可指定子集执行:/speckit-implement --filter T01,T02

Step 9 · /speckit-converge — 验证完整性

将代码库与规格、方案、任务逐项核对。若发现缺口,会自动追加新任务到 tasks.md;之后再次运行 /speckit-implement 并继续收敛,直到输出 Converged。

✅ Converged 才算完成

如果首次 converge 失败,继续实现新增任务,再次 converge — 直到真正收敛。这是规格与实现的"对账"过程,跳过会让技术债积累。

🔑 核心原则

🎯

Be explicit

明确表达你在构建什么、为什么 —— 把意图固化在文档里。

🚫

Don't focus on tech

规格阶段不要聚焦技术栈 —— 技术决策属于 plan.md。

🔄

Iterate & refine

编码前先迭代完善规格 —— clarify 阶段不要省。

✅

Validate first

编码开始前先验证需求和方案 —— analyze 是关键门。

🤖

Let agent handle

让编码智能体去处理实现细节 —— 人类聚焦意图与证据。
