主标题区

GitHub Spec Kit

用规格(spec)构建、修复 bug,或评估一个想法 — 与你的编码智能体一起。

Spec Kit 为你的编码智能体提供结构化的流程,让"意图"和"证据"始终领先于"实现"。你可以从规格驱动开发(SDD)、Bug 修复或想法评估任意一个入口开始。你可以一步一步执行,也可以自动化,甚至可以定制属于你自己的流程 — 包括软件研发之外的其他领域。

选择你的流程

你需要做什么从这里开始你将获得
构建一个新功能或应用 规格驱动开发(SDD) 一份贯穿规划、实施与收敛全过程的规格说明
诊断并修复缺陷行为 Bug 修复 经过评估的根因、限定范围的修复方案,以及留存的验证记录
判断一个想法是否值得投入 想法评估 有证据支撑的"推进 / 澄清 / 停止"决策

这三者是独立的入口,不是强制的连续阶段。SDD 是核心内置流程;Bug 修复和想法评估是捆绑提供的、可选用开启的扩展。

🎯 核心设计理念

Spec Kit 不是一个 AI 编码工具,而是一个 "让 AI 编码可被治理" 的流程框架。它的核心思路是:用结构化的规格(spec)与证据(evidence),让 AI 编码智能体的产出可被工程化地管理。

⚠️ 要解决的三大问题

痛点表现Spec Kit 的对策
意图漂移 一句话需求 → 直接生成代码 → 实现跑偏 先用 Markdown 规格把"要做什么"固化下来
证据缺失 AI 改完代码无法回答"为什么改、改得是否正确" 每个阶段产出可追溯的 Markdown artifact
流程锁定 团队被迫使用某一种开发模式 流程本身是数据(presets / extensions),可换可拼

🏛️ 分层架构

Spec Kit 采用 "内核 + 插件 + 包" 的分层设计,流程本身是数据。

🌟 为什么这是关键设计

Spec Kit 把流程当作数据,因此能容纳"小说写作流程"——只要能拆成 Define → Plan → Tasks → Implement → Converge(或近似版),就可以用 Spec Kit 来跑。

📊 与传统方式对比

维度传统开发模式Spec Kit 模式
需求表达 口头/即时消息,易丢失 Markdown spec.md,可 diff 可版本化
方案评审 PR 阶段才介入 spec 阶段即可介入,Lead 提前仲裁
任务拆解 Issue 列表,依赖关系弱 tasks.md 显式依赖图,可并行任务标 [P]
质量门禁 靠 CI + 手动 review /speckit-converge 自动对账
跨智能体迁移 上下文易断 规格即上下文,任何智能体接手都能理解
流程定制 改源码/换工具 装 preset/extension,无需改源码

💻 安装与初始化

# 1. 安装 CLI(基于 uv,Python 生态的现代包管理)
uv tool install specify-cli

# 2. 初始化项目(指定你用的 AI 智能体)
specify init my-project --integration copilot

# 3. 进入项目
cd my-project

执行完后,Spec Kit 会自动在你的仓库里:

  • 创建 .specify/ 目录(存放规格、计划、任务等 Markdown 产物)
  • 根据 --integration 生成对应 AI 工具的命令文件(如 .github/prompts/ 或 .claude/commands/)
  • 准备好模板和质量检查清单

📌 总结

🎓 核心要点
  • 三大入口:SDD(新建)、Bug Fix(修复)、Assessment(评估)正交可选
  • 九步内核:Constitution → Specify → Clarify → Plan → Checklist → Implement → Converge
  • 可扩展架构:流程是数据,可由 Bundles / Workflows / Presets / Extensions 组合
  • 38 种兼容:Copilot / Claude / Gemini / Codex / Cursor 等,无锁定
  • 企业可用:离线、防火墙、自托管目录,Windows / macOS / Linux 全平台
