📋 总览:Grill 是什么

"Grill" 直译为"炙烤/拷问",在 AI Coding 语境下指苏格拉底式追问(Socratic Interview)模式:让 AI 反过来向用户提问题,直到把方案/想法的每一个分支都问清楚、每个隐藏假设都挖出来。

它与传统"brainstorming"最大的区别:

维度Brainstorming(头脑风暴)Grilling(炙烤追问)
方向 探索"要做什么" 拷问"你确定这样做吗"
阶段 项目早期(从 0 到 1) 已经有方案/想法(从 1 到 ∞)
问题类型 开放式:谁用?做什么?不做什么? 封闭但深挖:为什么?如果 X 失败?边界情况?
停止条件 用户说"够了" 所有决策树分支都被问过
风格 温和引导 不留情面(relentlessly)

一句话理解:

  • Brainstorming:你有一个"模糊的方向",AI 帮你"打开想象"
  • Grilling:你有一个"具体的方案",AI 帮你"找出所有漏洞"

🎯 Grill 模式核心:苏格拉底式追问

Grill 模式有一个5 步标准循环,几乎所有 Grill 类 skill 都遵循:

1
接收方案
用户陈述计划/设计/想法
2
枚举分支
AI 列出所有决策点
3
顺序追问
一个一个分支问透
4
挖假设
找"你以为是但其实不是"
5
对齐/否决
共识 or 推翻重来
图 1:Grill 5 步循环(几乎所有 Grill 实现都基于此模式)

典型 Grill 问题示例

类型示例问题
Why(为什么) 为什么不用 PostgreSQL?为什么必须 7 天而不是 3 天?
What if(假设) 如果 QPS 涨 10 倍?如果服务挂了?如果用户是色盲?
Hidden assumption(隐藏假设) "所有人都用 Chrome"——真的所有吗?移动端呢?
Trade-off(权衡) 性能 vs 准确性?开发速度 vs 可维护性?选哪个,为什么?
Boundary(边界) 空字符串?0?null?负数?emoji?1MB 文件?
Cost(成本) 迁移成本?回滚成本?团队学习成本?云资源成本?

3 个核心 Grill 命令详解

1️⃣ /grill-me(最受欢迎)

类别:User-invoked,生产力

用途:"Relentlessly interviews you about a plan/design until every branch is resolved"

触发:"grill me about [我的计划]"

典型场景:已经写完 RFC,想"压力测试"一遍再发给团队

2️⃣ /grill-with-docs(作者最推荐)

类别:User-invoked,工程

用途:"A grilling session, but that helps you build a shared language with the AI, and document hard-to-explain decisions in ADR's."

触发:"grill-with-docs on this RFC"

额外能力:

  • 主动构建共享语言(domain modeling)
  • 更新 GLOSSARY.md(术语词典)
  • 沉淀ADR(架构决策记录)到 docs/
  • 变量/函数/文件命名一致,agent 减少 token 消耗

作者原话:"The single coolest technique in this repo."

3️⃣ /grilling(底层原语)

类别:Model-invoked,工程

用途:可复用的追问原语,被 /grill-me、/grill-with-docs、/triage、/wayfinder、/improve-codebase-architecture 共用

用户:通常不直接调用,被上层 skill 自动调用

适合:开发者自己 fork 写新 skill 时复用

Matt Pocock 的 4 大失败模式 + 4 大对应 skill

失败模式对应解决方案依赖 Grill?
#1 Misalignment(智能体没做你想要的) /grill-me、/grill-with-docs ✅ 直接
#2 Verbosity / Jargon mismatch(表达不一致) /grill-with-docs(构建共享语言) ✅ 直接
#3 Code doesn't work(代码不工作) /tdd、/diagnosing-bugs ❌ 间接(feedback loop)
#4 Ball of mud(代码腐烂) /to-spec、/improve-codebase-architecture ⚠️ 部分

🎯 Claude Code + Codex CLI 🚪 5 阶段 + 4 道门 📦 完整 spec 包

定位:Not an automatic implementer —— 是一个门控式 spec 流程,任何代码改动前必须通过 5 道关卡

5 阶段 + 4 道门

0
访谈
Question-by-question
1
需求 REQ-*
2
设计 DES-*
3
任务 + 验证
4
实施 + 验证

4 道门控(必须精确输入批准短语)

门号精确批准短语通过条件
门 1 批准访谈并进入需求阶段 所有访谈问题已回答
门 2 批准需求并进入设计阶段 所有 REQ-* 条目已 Approved
门 3 批准设计并进入任务阶段 DES-* 决策已记录
门 4 批准任务并开始实施 任务列表 + 验证计划

注意:通用确认("OK"、"1"、"next")无效,必须使用上述精确短语

产物结构

.specs/
└── 2026-10-14-feat-citation/
    ├── requirements.md   # REQ-001, REQ-002 ...
    ├── design.md         # DES-001, DES-002 ...
    └── tasks.md          # TASK-001, TASK-002 ...

依赖的 skill

  • grilling — 追问原语
  • requirements-engineering — 需求工程
  • design-documentation — 设计文档
  • spec-driven-development — SDD 主线
  • domain-modeling(可选) — 域建模

与 spec-kit 的关系:

  • 概念接近(都是门控 spec 流程)
  • 产出格式不同(.specs/日期/ vs spec-kit 的 specs/NNN-feature/)
  • 可手动桥接:把 grill-spec-flow 的 requirements.md 作为 /speckit-specify 的输入

🔗 Grill + spec-kit 组合(零冲突)

与 OpenSpec 不同,Grill 与 spec-kit 零冲突,因为 Grill 是前置追问,不写 spec 文档;spec-kit 是后置规范化,把方案变成可追溯 Markdown。

黄金路径

图 4:Grill 在 spec-kit 流程中的位置(夹在 RFC 和 specify 之间)

3 种推荐组合

组合 A:spec-kit + /grill-me(默认推荐)

适用:80% 的 feature,只需轻量拷问

分工:

  • RFC 写完 → /grill-me 拷问 1 轮(30 分钟)
  • 把回答整理成 bullet list
  • 把 bullet list 作为 /speckit-specify 的输入

学习曲线:极低

组合 B:spec-kit + /grill-with-docs(团队推荐)

适用:跨团队、长寿命的 feature(如 RFC-002 答案溯源)

分工:

  • RFC 写完 → /grill-with-docs(1-2 小时)
  • 自动产出 docs/adr/NNNN-xxx.md 和 GLOSSARY.md 更新
  • ADR 是 /speckit-specify 的黄金前置输入(直接 copy "Why this decision" 段落)
  • 术语统一后,所有 feature spec 命名一致

学习曲线:中(需要理解 ADR 概念)

组合 C:spec-kit + grill-spec-flow(高合规推荐)

适用:医疗/金融/高合规场景,需要"留痕"

分工:

  • 用 grill-spec-flow 跑完整 5 阶段(产出 .specs/日期/ 包)
  • 把 requirements.md 改写为 spec-kit 格式
  • 把 design.md 拆为多个 /speckit-specify feature

学习曲线:陡(精确短语 + 格式转换)

⚖️ Grill vs Superpowers brainstorming

这是最容易混淆的对比,明确区分清楚:

维度 🧠 Superpowers brainstorming 🔥 mattpocock /grill-me
目标 从 0 到 1(发散想法) 从 1 到 ∞(收敛漏洞)
输入 "我想做一个 X,但不知道细节" "我计划这样实现 X,你看怎么样?"
输出 设计文档、feature 列表、RFC "Survived / Revised / Killed" 三段式判断
问题类型 开放式:谁用?做什么? 封闭式:为什么?如果 X 怎么办?
态度 温和,鼓励 不留情面(relentlessly)
何时用 项目启动、新功能 0 阶段 RFC 完成后、写代码前
典型时长 1-2 小时 30-60 分钟
与 spec-kit 关系 前置(产生 RFC) 中夹(拷问 RFC 后再走 specify)
沉淀物 设计文档 ADR + Glossary(/grill-with-docs)
🎓 怎么选?
  • 只有模糊方向("我想做 AI 助手")→ brainstorming
  • 已有方案(RFC 写完)→ grill-me 或 grill-with-docs
  • 两者可以叠加:brainstorming 产生 RFC → grill-me 拷问 → /speckit-specify

🚫 反模式(什么时候不要用 Grill)

反模式后果正确做法
❌ 用 Grill 探索方向 AI 不知道问什么(没东西可拷问) 先用 brainstorming 出 RFC
❌ 一上来就 Grill 一个想法 被拷问到放弃 至少先写到 RFC 草稿阶段
❌ 装 3 个 Grill skill 同时跑 对话冲突,AI 不知道听哪个 挑 1 个(推荐 mattpocock)
❌ Grill 一个 1 行需求 没东西可问,AI 尬问 至少 1 段(200+ 字)再 Grill
❌ 用 Grill 替代 brainstorming 把"发散"环节跳过 Grill 是"反对意见",brainstorming 是"想法"
❌ Grill 后不更新 RFC 问题回答了但方案没改 把"Revised"清单写回 RFC
❌ 用 grill-spec-flow 不读门控短语 一直卡在门 1 先看 4 个精确短语

📌 结论

核心要点:

  1. Grill = 苏格拉底式追问,专门拷问已有方案,与 brainstorming 互补
  2. 3 个核心命令(都来自 mattpocock):
    • /grilling —— 底层原语,不直接用
    • /grill-me —— 个人快速拷问
    • /grill-with-docs —— 团队推荐,沉淀 ADR+Glossary
  3. 其他 6 个实现各有特色:Jekudy 3×4 结构化、Murder-Board 6 步审判、grill-spec-flow 5 阶段门控
  4. 与 spec-kit 零冲突:Grill 在 RFC 之后、specify 之前
  5. 本项目 80% 情况不需要 Grill;只有 RFC 复杂、跨团队、需要术语统一时启用
  6. 作者最推荐:/grill-with-docs(沉淀物 = spec-kit 黄金输入)
