🧬 3 大模式分类

这 14 个工具本质上只做 3 件事,理解了这一点就能快速选型:

🧠 模式 A:头脑风暴(Brainstorm)——"打开想象"

问题:"我想做 X,但不知道具体是什么"

输入:模糊方向、痛点描述

输出:feature 列表、RFC、设计文档

代表工具:

  • Superpowers brainstorming(最成熟)
  • awesome-claude-skills 的 brainstorming / deep-research / recursive-research
  • agentic-awesome-skills 的 brainstorming / before-you-build / idea-autopsy
  • OpenSpec explore(读代码的 brainstorming)

🔥 模式 B:Grill 拷问(Stress-test)——"找出所有漏洞"

问题:"我已经有方案,你看看有什么坑?"

输入:RFC、plan、design doc(已有具体方案)

输出:Survived / Revised / Killed 判断、ADR、Glossary

代表工具:

  • mattpocock/grill-me(个人拷问)
  • mattpocock/grill-with-docs(团队拷问 + ADR,作者最推荐)
  • RobMitt/grill-me-skill(单文件轻量版)
  • Jekudy/grillme-skill(3 waves × 4 lenses 结构化)
  • MbappeWU/murder-board(verdict 式审判)

🧩 模式 C:分解与规范化(Spec/Plan)——"落地成 spec"

问题:"想法有了,怎么变成可执行的 Markdown?"

输入:经 brainstorm + grill 过的方案

输出:requirements.md / design.md / tasks.md / proposal

代表工具:

  • Kiro(AWS 三件套)
  • OpenSpec propose(change 包)
  • joslynSmall/grill-spec-flow(5 阶段 + 4 门)
  • pardeep-kumar94/idea-to-pr(7 阶段)
  • Marvin marvin.plan()(Python 化)
🎯 关键洞察

spec-kit 的 /speckit-specify 属于模式 C(分解与规范化)。所以你问"用 brainstorm 工具还是 grill 工具还是 spec-kit",答案是:

  • 模式 A(brainstorm)在 spec-kit 之前:产生 RFC
  • 模式 B(grill)在 spec-kit 之前:拷问 RFC,沉淀 ADR/Glossary
  • 模式 C(spec-kit 本身):把方案变成可追溯 Markdown

🎯 5 个发现子阶段(全流程地图)

一个完整的"从模糊到 spec"流程,实际上包含 5 个子阶段,每个子阶段有对应工具:

① Idea(想法)
工具:无 / 自然语言
时长:1-2 天
状态:"我想做 X"
② Brainstorm(发散)
工具:brainstorming
时长:1-2 小时
状态:"X 的受众、痛点、约束"
③ Draft(草稿)
工具:OpenSpec explore / Marvin plan
时长:1-3 天
状态:"RFC v0.1"
④ Grill(拷问)
工具:grill-me / grill-with-docs / murder-board
时长:30-120 分钟
状态:"RFC v1.0 + ADR"
⑤ Spec(规范化)
工具:/speckit-specify
时长:10-30 分钟/feature
状态:"specs/NNN-feature/spec.md"

📑 14 个工具详细对比

🧠 模式 A · Brainstorm 类(4 个)

1. Superpowers brainstorming 强烈推荐

定位:Claude Code 官方 plugin 市场的方法论级 skill,SDD 的"标准前置"

核心能力:温和引导式提问,问 5-10 个关键问题

优势:

  • ✅ 与 spec-kit 零冲突(完美配对)
  • ✅ 强制发现,不让团队跳过
  • ✅ 配合 TDD、Code Review 全套
  • ✅ 社区最大(299K stars)

劣势:❌ 仅 Claude Code

适合:任何 spec-kit 项目的"发现阶段"

2. awesome-claude-skills 1000+ 推荐

定位:Claude Skills 目录,从中挑 1-2 个

核心能力:包含 brainstorming、deep-research、recursive-research

优势:

  • ✅ 覆盖面广(1000+)
  • ✅ 中英文混合
  • ✅ 单文件复制即用

劣势:❌ 不成体系,自己拼装

适合:在 brainstorming 之外,想加 research 能力

3. agentic-awesome-skills 2689+ 强烈推荐

定位:场景化 skills 集合,按"建前审查"挑

核心能力:包含 brainstorming、before-you-build、idea-autopsy、what-could-break、rich-elicitation

优势:

  • ✅ 精准场景化(每个 skill 对应一个明确场景)
  • ✅ 16+ 平台支持
  • ✅ 与 spec-kit 友好

劣势:❌ 新手不知道选哪个(5 个 skill 容易选错)

适合:已经有 RFC,想用 1-2 个 skill 做"建前审查"

4. OpenSpec explore 强烈推荐

定位:SDD 框架,4 命令轻量流程

核心能力:/opsx:explore 读你的代码,给 2-3 个方案对比 + tradeoffs

优势:

  • ✅ 轻量(4 命令)
  • ✅ 唯一会读你代码的 brainstorm 工具
  • ✅ 30+ IDE 支持

劣势:⚠️ 与 spec-kit 输出格式略不同(单 change 目录 vs specs/)

适合:已有项目加新功能,需要"读代码给方案"

🔥 模式 B · Grill 类(6 个)

5. mattpocock/grill-me 强烈推荐

定位:"Relentlessly interviews you until every branch is resolved"

核心能力:对一个 plan/design 持续追问,直到所有决策树分支都解决

优势:

  • ✅ 作者是最有影响力的 TypeScript 教育者
  • ✅ 290.8K stars 背书
  • ✅ 多 IDE 支持(Claude/Codex/Copilot/Gemini/Cursor 等)
  • ✅ 零配置(不依赖 setup)

劣势:❌ 不沉淀文档

适合:个人快速拷问方案,30-60 分钟

6. mattpocock/grill-with-docs 作者最推荐 ⭐

定位:"Grilling + 域建模/ADR 沉淀"——作者称"the single coolest technique"

核心能力:

  • 追问(同 grill-me)
  • 更新 GLOSSARY.md(术语词典)
  • 沉淀 docs/adr/NNNN-xxx.md(架构决策记录)
  • 变量/函数命名统一(减少 agent token)

优势:

  • ✅ 沉淀物是 spec-kit 黄金输入(直接 copy "Why this decision")
  • ✅ 跨团队术语统一
  • ✅ 零配置(用默认 docs/adr/ 位置)

劣势:⚠️ 中等学习曲线(需要理解 ADR)

适合:跨团队、长寿命的 feature(如本项目 RFC-002)

7. RobMitt/grill-me-skill 推荐

定位:单文件轻量版 grill-me,社区认知度最高(928 stars)

核心能力:对 plan 追问 + 决策树分支解析

优势:

  • ✅ 单文件 SKILL.md,1 分钟安装
  • ✅ 完全独立(不依赖整个 plugin)

劣势:

  • ❌ 不沉淀 ADR/Glossary
  • ❌ 仅 Claude Code

适合:只想拷问一下方案、不想装整个 plugin 的个人

8. Jekudy/grillme-skill 可选

定位:3 waves × 4 lenses 结构化追问

核心能力:

  • Wave 1:Discovery(目标/痛点/受众)
  • Wave 2:Design(架构/接口/数据流)
  • Wave 3:Operation(部署/监控/成本)
  • × 4 个透镜:🔬 Technical / 👤 UX / 💼 Business / ⚠️ Risk

优势:✅ 框架化,不会漏

劣势:⚠️ 比 mattpocock 啰嗦

适合:喜欢"按框架走"的人

9. MbappeWU/murder-board 可选

定位:"Murder Board"——6 步审判,verdict 式输出

6 步:Establish → Identify → Attack → Stress-test → Counter → Verdict

输出:SURVIVED / REVISED / KILLED(决断式)

适合:做"go/no-go"决策,给高层看的 verdict

劣势:❌ 不沉淀 ADR

10. mcdays94/pocock-agents 小众

定位:grill + plan + dispatch 3 合 1

核心能力:拷问 → 拆任务 → 派发多 agent

适合:想要"拷问完直接派发"的人

🧩 模式 C · Spec/Plan 规范化类(4 个)

11. Kiro (AWS) 看场景

定位:AWS 的 SDD 完整 IDE 工具,Specs 三件套

核心能力:requirements.md / design.md / tasks.md

优势:

  • ✅ 企业级、UI 完整
  • ✅ Requirements-First / Design-First 两种模式

劣势:

  • ❌ 绑定 Kiro IDE(生态封闭)
  • ❌ 闭源(AWS)
  • ❌ 与 spec-kit 互斥

适合:愿意换 IDE 的企业团队

12. OpenSpec propose 推荐

定位:OpenSpec 的后半段,把 explore 出的方案变 change 包

核心能力:

openspec/changes/answer-citation/
├── proposal.md
├── specs/
├── design.md
└── tasks.md

优势:

  • ✅ 完整 change 包(可一次性 review)
  • ✅ 30+ IDE
  • ✅ 结构上类似 spec-kit

劣势:⚠️ 与 spec-kit 思路略不同(单 change 目录)

适合:同时用 OpenSpec + spec-kit 的人群

13. joslynSmall/grill-spec-flow 特殊场景

定位:5 阶段 + 4 道精确门控的 spec 流程

4 道精确门:必须用精确中文短语才放行

产出:.specs/2026-10-14-feat/{requirements,design,tasks}.md

优势:

  • ✅ 极致合规(每步必须批准)
  • ✅ 留痕完整

劣势:

  • ❌ 学习曲线陡(精确短语)
  • ❌ 速度慢
  • ⚠️ 与 spec-kit 需手动桥接

适合:医疗/金融/政府高合规场景

14. pardeep-kumar94/idea-to-pr 小众

定位:7 阶段 idea→PR 全自动管线

适合:个人项目,1 个人从 0 到 1

📦 其他/不推荐(3 个)

15. Marvin (Python) Python only

定位:编程式多 agent 框架

优势:✅ Python 类型安全

劣势:❌ Python only / 需自己写发现逻辑

16. Amplifier (Microsoft) 早期

定位:微软的多 agent 框架

状态:⚠️ 早期预览,无显式发现阶段

17. Eigent 无发现

定位:多 agent 框架

劣势:❌ 无发现阶段

🌳 统一决策树(终极版)

🔗 3 种推荐组合(spec-kit + 工具)

对发现阶段工具的常见组合做了归类,本项目绝大多数情况用组合 1,复杂 feature 用组合 2。

⭐ 默认 组合 1:仅 spec-kit(80% 场景)

触发条件:已有 RFC,功能清晰,直接拆 feature

工具清单:只有 spec-kit(已装)

流程:RFC → /speckit-specify → /speckit-plan → /speckit-tasks → /speckit-implement → /speckit-converge

本项目适用:RFC-002 答案溯源(已 Approved,直接走)

⭐ 推荐 组合 2:spec-kit + Superpowers + mattpocock(15% 场景)

触发条件:跨团队、长寿命 feature,需要术语统一

工具清单:

  • Superpowers brainstorming(发散阶段)
  • mattpocock /grill-with-docs(拷问 + 沉淀 ADR/Glossary)
  • spec-kit 全套

流程:brainstorming(1-2h)→ RFC → /grill-with-docs(1-2h,产出 ADR)→ /speckit-specify

本项目适用:下一个大型项目(AI 工作台)

⚠️ 选配 组合 3:spec-kit + OpenSpec(3% 场景)

触发条件:已经在用 OpenSpec,想保留 OpenSpec 格式

工具清单:

  • OpenSpec explore + propose
  • spec-kit /speckit-constitution + /speckit-specify

流程:explore → propose(OpenSpec change 包)→ /speckit-specify(转 spec-kit 格式)

本项目适用:不推荐(有格式转换成本)

🛡️ 特殊 组合 4:spec-kit + grill-spec-flow(2% 场景)

触发条件:高合规/医疗/金融,需要"门控"留痕

工具清单:

  • grill-spec-flow(5 阶段 + 4 门)
  • spec-kit 接手 requirements.md

本项目适用:不推荐(速度慢,本项目无合规压力)

🚫 反模式(从两份文档汇总)

反模式 后果 正确做法 来自
❌ 装太多 skill,挑花眼 2 周还在选,没开始 先装 1-2 个最常用,跑通再加 discovery-tools
❌ 不评估项目状态直接选 用错工具,产出无效 先看决策树,定位项目状态 discovery-tools
❌ 用 Kiro 但要切换 IDE 团队抵触,推不动 已经在 Claude Code 生态,选 Superpowers / OpenSpec discovery-tools
❌ 选了发现工具但跳过 spec-kit 产出无结构化,无法 Converge 发现阶段 → spec-kit 是连续流程 discovery-tools
❌ POC 阶段走 spec-kit POC 失败,白写 spec POC 阶段用 brainstorming + recursive-research discovery-tools
❌ 用 Marvin 写非 Python 项目 不匹配 非 Python 项目用 OpenSpec / Superpowers discovery-tools
❌ 用 Grill 探索方向 AI 不知道问什么(没东西可拷问) 先用 brainstorming 出 RFC grill-skills
❌ 一上来就 Grill 一个想法 被拷问到放弃 至少先写到 RFC 草稿阶段 grill-skills
❌ 装 3 个 Grill skill 同时跑 对话冲突,AI 不知道听哪个 挑 1 个(推荐 mattpocock) grill-skills
❌ Grill 一个 1 行需求 没东西可问,AI 尬问 至少 1 段(200+ 字)再 Grill grill-skills

核心原则(本项目)

  1. 默认不装发现工具——80% 的 feature 走 spec-kit 就够
  2. 遇到跨团队 feature 才装——brianstorming + grill-with-docs

  4. 任何"我以为"都过一遍 grill-me——5 分钟可能省 5 天返工
  5. grill-with-docs 的产物是 spec-kit 黄金输入——ADR 直接 copy 到 spec 的"决策依据"

✅ 选型检查清单

选型前必问的 5 个问题

  1. 我的项目状态是 5 种场景中的哪个?(完全模糊 / 方向清楚 / 有 RFC / 等 grill / 直接拆 spec)
  2. 我在哪个 IDE?(Claude Code / Kiro / 其他)
  3. 团队/个人使用?(影响学习曲线容忍度)
  4. 需要沉淀 ADR/Glossary 吗?(决定 grill-me vs grill-with-docs)
  5. 是否有 Python 强需求?(决定是否考虑 Marvin)

实操前 3 个准备

  • 准备 1 段自然语言描述(2-5 句 / 200+ 字)
  • 决定装 1 个还是多个工具(默认 1 个,跨团队 2 个)
  • 决定安装路径(全局 vs 项目级)

选错工具的 5 个信号(需要切换)

  • 用 1 周后,产出的 spec 质量反而更差
  • 团队成员抱怨"太复杂了"
  • 工具的输出与 spec-kit 格式冲突
  • 装的工具 1 个月没碰过
  • 文档 ADR 沉淀后从未被引用过
