📜 1. /speckit-constitution

/speckit-constitution

必做 项目级(只跑 1 次,变更时再跑) 写 constitution.md Scope Guard:只写 .specify/memory/constitution.md

功能

创建或更新项目宪法(governance 文档),定义原则、版本管理、修订流程。

输入

/speckit-constitution
# 或者带具体原则描述:
/speckit-constitution 8 条原则:可观测性、TDD、ADR 留痕...

输出

.specify/memory/constitution.md
  - Core Principles(原则 1-N)
  - Governance(治理)
  - 版本号(SemVer)
  - Sync Impact Report(临时 HTML 注释)

关键规则

  • Scope Guard:只能写 constitution.md,不能改代码或 spec
  • SemVer:MAJOR(移除/重定义原则)/MINOR(新原则)/PATCH(措辞/typo)
  • 4 层模板解析栈:project overrides → preset layers → extension layers → core template
  • Sync Impact Report:作为 HTML 注释加在文件顶部,commit 前必须删除
  • 占位符:[ALL_CAPS_IDENTIFIER] 形式,必须全部替换或标记 TODO

本项目已有

v1.1.0,8 条原则(详见 constitution.html)

常见坑

  • ❌ 在宪法里写"feature 应该用 React"(太具体)→ ✅ 写"技术决策需要 ADR 留痕"(原则级)
  • ❌ 忘记删除 Sync Impact Report → commit 污染
  • ❌ 改宪法时混了 feature 实现请求 → Scope Guard 会拒绝

📝 2. /speckit-specify

/speckit-specify

必做 每个 feature 1 次 写 spec.md 生成 checklists/requirements.md

功能

把"自然语言 feature 描述"转成结构化 spec.md(必填 6 段 + 选填 3 段),并生成 Spec Quality Checklist(17 项)。

输入

/speckit-specify [feature 的自然语言描述]

# 例子:
/speckit-specify 段落 ID 生成器,为每个文档段落生成稳定的 hash 引用
/speckit-specify 用户登录支持手机号 + 邮箱双因子认证
/speckit-specify 流式定价,按 token 实时计费

参数注意事项(详见 specify.html):

  • ✅ DO:写"做什么/为什么/谁用",200-500 字最佳
  • ❌ DON'T:写技术栈(React/PostgreSQL)、文件结构、API 路由
  • ❌ DON'T:1-2 句话太短(无法产生有效 spec)
  • ❌ DON'T:一上来给一个"模糊方向"(先 brainstorm)
  • ✅ 硬规则:一次/speckit-specify 只能写一个 feature

输出

specs/
└── 003-citation-segment-id/        # 默认 NNN 顺序编号(可在 init-options.json 改 timestamp)
    ├── spec.md
    └── checklists/
        └── requirements.md         # 17 项 Spec Quality Checklist

spec.md 6 个必填段

  1. User Scenarios & Testing(用户故事 + 验收场景)
  2. Requirements(Functional Requirements,FR-### 可测)
  3. Key Entities(数据实体)
  4. Success Criteria(可量化、技术无关)
  5. Assumptions(假设)
  6. Edge Cases(边界情况)

3 个选填段

  • Dependencies(依赖)
  • Out of Scope(不做什么)
  • Open Questions(未决问题)

关键规则

  • Max 3 个 [NEEDS CLARIFICATION: ...] 标记
  • 17 项 Spec Quality Checklist(requirements.md)
  • 编号规则:从 .specify/init-options.json 读 feature_numbering(默认 sequential,即 001,002,...)
  • branch ≠ dir:spec 目录名和 git 分支名独立(虽然可以相同)
  • .specify/feature.json:记当前 feature dir 路径,下游命令通过它定位

❓ 3. /speckit-clarify

/speckit-clarify

强烈推荐 每个 feature 最多 1 次 更新 spec.md 最多问 5 个问题

功能

对当前 spec 做结构化歧义扫描,问最多 5 个高度针对性的澄清问题,答案直接写回 spec.md。

输入

/speckit-clarify
# 或者指定重点:
/speckit-clarify 重点关注数据安全和性能

输出

在 spec.md 中:

  • 新增 ## Clarifications 段
  • 新增 ### Session YYYY-MM-DD 子段
  • 每个答案一行 bullet:- Q: 问题 → A: 答案
  • 同步更新相关章节(Requirements / Success Criteria / Edge Cases ...)
  • 如果有 checklists/requirements.md,自动重新勾选

13 个歧义扫描类别

1. Functional Scope & Behavior核心目标 / 边界 / 用户角色
2. Domain & Data Model实体 / 唯一性 / 生命周期
3. Interaction & UX Flow关键路径 / 错误态 / 无障碍
4. Non-Functional Quality性能 / 可扩展性 / 可靠性 / 可观测性 / 安全 / 合规
5. Integration & External Deps外部 API / 数据格式 / 协议版本
6. Edge Cases & Failure负面场景 / 限流 / 冲突解决
7. Constraints & Tradeoffs技术约束 / 拒绝的备选
8. Terminology & Consistency术语统一 / 避免同义词
9. Completion Signals可测试的验收 / DoD
10. Misc / PlaceholdersTODO 标记 / 模糊形容词
...(共 13 类,详见 SKILL.md)

问题格式

每个问题遵循严格格式:

**Question:** [完整问句,以 ? 结尾]? (FR-023)

Why it matters: [1 句话说明为什么这影响交付]

**Recommended:** Option [X] - [1-2 句理由]

| Option | Description |
|--------|-------------|
| A | ... |
| B | ... |
| C | ... |
| Short | 提供自定义短答(<=5 词) |

You can reply with the option letter (e.g., "A"), accept the recommendation by saying "yes" or "recommended", or provide your own short answer.

硬规则

  • 最多 5 个问题(超过会停止)
  • 每次问 1 个,不一次列出全部
  • 不剧透未来问题
  • 每个问题必推荐一个选项 + 理由
  • 问题必须以 ? 结尾的完整问句(不能是标签如"Acceptance matrix")

何时跳过

⚠️ 可以跳过但会警告:"下游返工风险增加"

🛠️ 4. /speckit-plan

/speckit-plan

必做 每个 feature 1 次 写 plan.md + research.md + data-model.md + contracts/ + quickstart.md 2 个阶段:Phase 0 研究 + Phase 1 设计

功能

把 spec 转成技术方案。包含 2 个阶段:

  • Phase 0: Outline & Research — 提取技术上下文中的 NEEDS CLARIFICATION,产出 research.md
  • Phase 1: Design & Contracts — 产出 data-model.md、contracts/、quickstart.md

输入

/speckit-plan
# 或者带指引:
/speckit-plan 优先用 PostgreSQL + pgvector,因为我们已有 PG 经验

输出(5 个文件)

specs/003-citation-segment-id/
├── plan.md              # 主方案(技术栈、架构、阶段、Constitution Check)
├── research.md          # Phase 0:每个 NEEDS CLARIFICATION 的决策
├── data-model.md        # 实体 / 字段 / 关系 / 状态机
├── contracts/           # API 契约(若有)
│   ├── openapi.yaml     # 例:对外 API
│   └── events.md        # 例:事件 schema
└── quickstart.md        # 端到端验证剧本

plan.md 关键段

  • Technical Context(语言 / 框架 / 存储 / 依赖) — 未知项标 NEEDS CLARIFICATION
  • Constitution Check(每条原则:✅ 符合 / ⚠️ 例外 + 理由 / ❌ 违规)
  • Project Structure(目录树)
  • Phases(Setup / Foundational / User Story phases / Polish)

Constitution Check 强约束

plan 必须逐条对账 constitution.md:

  • ✅ 符合:直接列
  • ⚠️ 例外:必须给理由
  • ❌ 违规:ERROR,plan 拒绝生成

关键规则

  • 绝对路径操作文件系统;相对路径写在文档里
  • Constitution 违规 → ERROR,不绕过
  • NEEDS CLARIFICATION 没解决 → ERROR
  • 无外部接口(纯内部工具) → 跳过 contracts/

📋 5. /speckit-checklist

/speckit-checklist

选做 每个 feature 多次(不同 domain) 追加到 checklists/{domain}.md 最多 5 个澄清问题

功能

生成"需求的单元测试"(Unit Tests for English)——测的是需求写得好不好,不是代码 work 不 work。

⚠️ checklists/requirements.md(由 /speckit-specify 生成)是内置的 spec 质量检查,和这个命令生成的 checklist 不同。前者由 AI 维护,后者由 reviewer 勾选。

输入

/speckit-checklist UX
/speckit-checklist API 安全
/speckit-checklist 性能与可观测性

输出

specs/003-citation-segment-id/checklists/
├── ux.md           # 每次调用生成一个 domain 文件
├── api.md          # 可以追加
└── security.md     # 可继续追加

核心原则

测需求质量,不测实现:

❌ 错误(测实现)✅ 正确(测需求质量)
Verify landing page displays 3 episode cards Are the exact number and layout of featured episodes specified? [Completeness]
Test hover states work on desktop Are hover state requirements consistently defined? [Consistency]
Confirm logo click navigates home Are navigation requirements clear for all clickable brand elements? [Clarity]

8 个质量维度

  • Completeness / Clarity / Consistency / Measurability
  • Coverage / Edge Cases / Non-Functional / Dependencies & Assumptions

ID 编号

CHK001, CHK002, ... 全局递增;新文件从 001 开始,追加文件接续

关键规则

  • 永不删除已有 checklist 内容,只追加
  • 每条都 [ ](reviewer 勾选,AI 不自动标 [x])
  • ≥80% 条目必须带 traceability 引用([Spec §X.Y] 或 [Gap])
  • 最多 5 个澄清问题(分两轮:Q1-Q3 必问,Q4-Q5 可选)

✅ 6. /speckit-tasks

/speckit-tasks

必做 每个 feature 1 次 写 tasks.md 按 user story 拆,带 [P] 并行标记

功能

把 plan + spec 转成可立即执行的 task 列表,按 user story 分阶段(每个 user story 独立可测)。

输入

/speckit-tasks
# 或者带约束:
/speckit-tasks 不用 TDD,跳过测试任务

输出

specs/003-citation-segment-id/tasks.md

# 结构:
## Phase 1: Setup              # 项目初始化
## Phase 2: Foundational       # 阻塞所有 user story 的前提
## Phase 3: User Story 1 (P1)  # 一个 user story 一个 phase
## Phase 4: User Story 2 (P2)
## Phase 5: Polish             # 收尾

Task 严格格式(必填)

- [ ] T001 [P] [US1] Create User model in src/models/user.py
     ↑     ↑    ↑
   复选   并行  user story 标签(只在 user story 阶段)
   框     标记  (Setup/Foundational/Polish 阶段无标签)

5 个反例(都会被拒绝):

  • ❌ - [ ] Create User model(缺 ID 和 Story 标签)
  • ❌ T001 [US1] Create model(缺 checkbox)
  • ❌ - [ ] [US1] Create User model(缺 Task ID)
  • ❌ - [ ] T001 [US1] Create model(缺文件路径)
  • ❌ - [ ] T001 Create project structure per implementation plan(Setup 阶段 OK,但缺 Story 标签在其他阶段)

关键规则

  • 每个 user story 必须独立可测
  • [P] 标记 = 不同文件 + 无未完成依赖
  • Tests 可选:spec 没要求或 user 没明确要求 TDD → 不生成
  • MVP 范围:通常 = User Story 1
  • 总数 ≤ 40(若 > 40,合并低优项)
  • data-model.md 中的约束(如 max length)必须逐字引用在 task 描述里

🔍 7. /speckit-analyze

/speckit-analyze

选做 只读 / 不改文件 输出分析报告 ≤ 50 条 finding

功能

对 spec.md + plan.md + tasks.md 做非破坏性一致性 + 质量分析,输出报告(不写文件)。

输入

/speckit-analyze
# 或指定重点:
/speckit-analyze 重点检查 constitution 一致性

输出

仅屏幕报告(无文件):

## Specification Analysis Report
| ID | Category | Severity | Location | Summary | Recommendation |
|----|----------|----------|----------|---------|----------------|
| A1 | Duplication | HIGH | spec.md:L120 | ... | ... |
| B2 | Ambiguity | MEDIUM | spec.md:L89 | "fast" 未量化 | ... |
| ... |

## Coverage Summary
| Requirement Key | Has Task? | Task IDs |
| FR-001 | ✅ | T012, T013 |
| FR-008 | ❌ | - |   ← 覆盖缺失!

## Constitution Alignment Issues
- ⚠️ plan.md §3 与 Constitution II(测试覆盖率)冲突

## Metrics
- Total Requirements: 12
- Total Tasks: 47
- Coverage: 11/12 = 92%

6 个检测通道

  • A. Duplication — 重复需求(找可合并)
  • B. Ambiguity — "fast/scalable/secure" 等模糊形容词
  • C. Underspecification — 缺对象 / 缺可测结果
  • D. Constitution Alignment — 违反 constitution MUST 原则
  • E. Coverage Gaps — 需求 0 task / task 0 需求
  • F. Inconsistency — 术语漂移 / 任务顺序冲突 / 实体缺失

4 个严重度

  • 🔴 CRITICAL:Constitution MUST 违反 / P1 story 阻塞
  • 🟠 HIGH:重复 / 冲突 / 安全模糊 / 不可测
  • 🟡 MEDIUM:术语漂移 / 缺非功能 / 边缘 case 模糊
  • 🟢 LOW:措辞 / 风格

关键规则

  • 严格只读:不改任何文件
  • ≤ 50 条 finding:超出汇总在 overflow summary
  • 建议修复:报告末尾提供(用户明确批准后才动)
  • Constitution 不可协商:冲突永远是 CRITICAL

⚙️ 8. /speckit-implement

/speckit-implement

必做 每个 feature 1 次 写代码 + 标 [X] 检查 checklist 门控

功能

按 tasks.md 逐 task 执行实施。每完成一个 task,把 [ ] 改成 [X]。

输入

/speckit-implement
# 或带筛选:
/speckit-implement 只跑 T012-T020

执行流程

  1. 检查 prerequisites(spec/plan/tasks 存在)
  2. 检查 checklists/ 状态(全 [x] 才允许;否则询问)
  3. 检测 git/docker/eslint 等,创建/补全 ignore 文件
  4. 按 phase 顺序执行:
    • Phase 1: Setup
    • Phase 2: Foundational(blocking)
    • Phase 3-N: User Stories(按优先级)
    • Final: Polish
  5. 每个 task 完成后标 [X]

Checklist 门控

如果 checklists/ 目录里有未完成的项:

| Checklist   | Total | Checked | Unchecked | Status |
|-------------|-------|---------|-----------|--------|
| ux.md       | 12    | 12      | 0         | ✓ PASS |
| test.md     | 8     | 5       | 3         | ✗ FAIL |

Some checklists have unchecked items.
Do you want to proceed with implementation anyway? (yes/no)

只有用户回答 yes/proceed/continue 才继续。

执行规则

  • Setup 先于所有 user story
  • Foundational 必须完成才能跑 user story
  • [P] 任务可并行(不同文件,无依赖)
  • TDD(若 spec 要求):测试任务先于实现
  • 失败停止:非并行任务失败即停
  • 完成后必标 [X]

ignore 文件自动检测

检测项目栈,自动创建/补全:

  • git repo → .gitignore
  • Node.js → node_modules/、dist/ 等
  • Python → __pycache__/、.venv/ 等
  • Docker → .dockerignore
  • ESLint / Prettier → 对应 ignore
  • ...

🔁 9. /speckit-converge

/speckit-converge

选做 每个 feature 多次 追加 Phase N: Convergence 到 tasks.md append-only,不重写

功能

对比当前代码和 spec.md + plan.md + tasks.md,找出未完成的工作,追加到 tasks.md,然后跳回 /speckit-implement 继续做。

输入

/speckit-converge

输出

追加(不改、不删、不重排)到 tasks.md:

## Phase 99: Convergence

- [ ] T042 Add append-only guard in path/to/tasks.py per FR-003 (missing)
- [ ] T043 Fix race condition in concurrent writes per SC-002 (partial)
- [ ] T044 CRITICAL: Remove hardcoded API key per Constitution V (contradicts)
- [ ] T045 Review and remove unused helper util_X per plan §3.2 (unrequested)

4 个 gap 类型

  • missing — 代码完全没有
  • partial — 有但不完整
  • contradicts — 代码与 spec/constitution 冲突
  • unrequested — 代码做了 spec/plan/tasks 没要求的事(只追加,提示 review)

3 个结局

  • converged — 没找到 actionable finding,报告 "✅ Converged"
  • tasks_appended — 追加了 N 个 task,建议跑 /speckit-implement 继续
  • prerequisite_missing — spec/plan/tasks 缺一个,直接 abort 提示跑哪个

关键规则

  • append-only:永远不重写 tasks.md 已存在内容
  • 不动 spec/plan:converge 只动 tasks.md
  • 不动代码:补全是 /speckit-implement 的活
  • Constitution 必须最先且标 CRITICAL
  • 若已 converged:tasks.md 字节级不变(连空 header 都不加)

替代方案

specify extension add github
/speckit-github-taskstoissues

关键规则

  • 必须 GitHub remote(否则 abort)
  • 去重:跑前查现有 issues,T\d{3,} 模式匹配 task ID
  • 分页:cursor-based,直到所有 task ID 匹配或无下一页
  • 标题:T001: <description>(ID 写一次)

🔗 跨命令状态同步(关键概念)

10 个命令看似独立,实际通过 3 个机制紧密耦合:

机制 1:.specify/feature.json

由 /speckit-specify 写入:

{
  "feature_directory": "specs/003-citation-segment-id"
}

下游所有命令(clarify / plan / tasks / implement / converge ...)通过它找到当前 feature。

机制 2:check-prerequisites.sh

大多数命令调用的通用前置检查脚本:

.specify/scripts/bash/check-prerequisites.sh --json --paths-only
#  返回 JSON:
{
  "FEATURE_DIR": "/abs/path/to/specs/003-citation-segment-id",
  "FEATURE_SPEC": "/abs/path/to/spec.md",
  "IMPL_PLAN": "/abs/path/to/plan.md",
  "TASKS": "/abs/path/to/tasks.md",
  "AVAILABLE_DOCS": ["spec.md", "plan.md", "tasks.md", ...]
}

不同 flag 控制严格度:

  • --json --paths-only:只返路径(plan 阶段用)
  • --require-tasks --include-tasks:要求 tasks.md 存在(implement/converge)
  • --require-spec --require-tasks:两个都要(analyze/converge)

机制 3:Constitution 共享

.specify/memory/constitution.md 是全局文件,所有 feature 命令都会读。

🪝 Extension Hooks(扩展点)

每个 spec-kit 命令都有前/后 hook 点,可通过 .specify/extensions.yml 注册自定义行为。

配置格式

# .specify/extensions.yml
hooks:
  before_specify:
    - extension: git.branch.create
      enabled: true
      optional: false  # 必须执行
  after_plan:
    - extension: slack.notify
      enabled: true
      optional: true   # 提示但不阻塞
  before_implement:
    - extension: tdd.run_tests
      enabled: true
      optional: false

命令 → Hook 点对照

命令before hookafter hook
constitution✅✅
specify✅✅
clarify✅✅
plan✅✅
tasks✅✅
checklist✅✅
analyze✅✅
implement✅✅
converge✅✅
taskstoissues✅✅

Hook 调用规则

  • optional: false → 必须执行,失败阻塞命令
  • optional: true → 提示用户可手动执行,不阻塞
  • Hook 名 a.b.c → 命令 /speckit-a-b-c(点换横线)
  • YAML 解析失败 → 不静默,告知用户没跑过哪些 mandatory hook
  • enabled: false → 跳过(缺省视为 enabled)

⚠️ 10 个常见错误(从 SKILL.md 抽取)

错误影响正确做法
❌ /speckit-specify 时一句话模糊方向 spec 质量差,plan 阶段要重写 先用 brainstorm / grill,出 200+ 字再 specify
❌ /speckit-specify 时混了多 feature 违反 1 invoke = 1 feature 硬规则 每个 feature 独立跑 1 次
❌ /speckit-specify 时写了技术栈 spec 阶段混入实现细节 spec 只写 WHAT/WHY,不写 HOW
❌ /speckit-clarify 跳过 下游返工风险增加 至少跑 1 轮,把 [NEEDS CLARIFICATION] 清掉
❌ /speckit-clarify 一次性问完所有 违反"每次问 1 个"规则 AI 自然会一次问 1 个,别催
❌ /speckit-plan 不做 Constitution Check 违反 constitution MUST 时应该 ERROR 确保 plan §Constitution Check 全部 ✅ 或 ⚠️ + 理由
❌ /speckit-tasks 写"X 阶段:加个功能"等模糊任务 无法独立测试 / 无法定位文件 严格格式:- [ ] T### [P?] [US?] 描述 with file/path
❌ /speckit-implement 时未跑 /speckit-analyze 隐藏的一致性问题到 implement 才暴露 implement 前必跑 analyze
❌ /speckit-implement 跳过 checklist 门控 需求质量未验证就开始写代码 让 checklist 全部 [x] 再继续(或显式 yes)
❌ /speckit-converge 后没跑 implement 追加的 task 永远躺在那 converge 后必跑 implement 一次

🎓 一句话总结:

  • 5 必做:constitution(1 次)、specify(每 feature)、plan、tasks、implement
  • 3 强烈推荐:clarify(扫歧义)、checklist(需求测试)、analyze(一致性)
  • 1 选做:converge(PR 前补漏)
  • 1 弃用:taskstoissues(用 github extension)
  • 3 共享机制:feature.json + check-prerequisites.sh + constitution.md
  • 10 扩展点:每个命令都有 before/after hook
